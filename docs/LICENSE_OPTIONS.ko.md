# Apache-2.0과 AGPL-3.0 선택 안내

이 문서는 법률 자문이 아니라 프로젝트 운영 결정을 위한 요약입니다. 공개 배포 전 실제 라이선스 원문과 의존성 호환성을 다시 검토해야 합니다.

## 공통점

둘 다 널리 쓰이는 오픈소스 라이선스이며 다음을 허용합니다.

- 개인·기업의 사용
- 상업적 이용
- 코드 열람과 수정
- 재배포

따라서 AGPL이 “비상업용” 라이선스인 것은 아닙니다.

## Apache License 2.0

쉽게 말하면 다음과 같습니다.

> 누구나 OwnContext를 사용하고 수정하며 상업 제품에 포함할 수 있다. 다만 저작권·라이선스 고지를 유지해야 한다.

주요 효과:

- 기업과 다른 오픈소스 프로젝트가 도입하기 쉽습니다.
- 수정한 코드를 공개하지 않고 제품이나 서비스에 포함할 수 있습니다.
- 명시적인 특허 라이선스와 특허 보복 조항이 있습니다.
- 대형 사업자가 코드를 가져가 폐쇄형 서비스를 만들어도 소스 공개를 강제하기 어렵습니다.

적합한 우선순위:

- 최대한 많은 AI 앱과 배포판에 포함되는 것이 중요함
- 기업·개발자 생태계의 채택 장벽을 낮추고 싶음
- 수익 모트를 코드 독점보다 브랜드, 운영, 동기화, 커넥터 품질에 둠

## GNU Affero General Public License 3.0

쉽게 말하면 다음과 같습니다.

> 수정한 OwnContext를 배포하거나 네트워크 서비스로 사용자에게 제공하면, 해당 사용자에게 대응 소스 코드를 제공해야 한다.

주요 효과:

- 수정본을 SaaS로만 제공하는 방식까지 공개 의무를 확장합니다.
- 커뮤니티 코드를 이용한 폐쇄형 호스팅 포크를 억제하는 데 유리합니다.
- AGPL 코드와 결합·배포되는 구성요소의 공개 의무를 신중하게 검토해야 합니다.
- 일부 기업과 앱 생태계는 법무·정책상 AGPL 의존성을 피합니다.

적합한 우선순위:

- 서비스 사업자도 코어 수정사항을 커뮤니티에 환원하게 하는 것이 중요함
- 도입 범위보다 공유 소프트웨어의 지속성을 우선함
- 상용 예외 라이선스나 듀얼 라이선스를 직접 운영할 역량이 있음

## 이 프로젝트에서의 실제 선택 기준

| 질문 | 그렇다면 기울어지는 선택 |
| --- | --- |
| Claude·Codex 외 여러 제품에 널리 내장되는 것이 최우선인가? | Apache-2.0 |
| 경쟁사가 코어를 수정해 폐쇄형 클라우드로 제공하는 것을 막고 싶은가? | AGPL-3.0 |
| 커넥터 SDK를 기업도 부담 없이 채택해야 하는가? | Apache-2.0 |
| 관리형 동기화 서버의 개선도 반드시 공개되길 원하는가? | AGPL-3.0 |

혼합 전략도 가능합니다. 예를 들어 코어 서버는 AGPL, 데이터 스키마와 커넥터 SDK는 Apache로 둘 수 있습니다. 다만 패키지 경계와 결합 방식을 법률적으로 검토해야 하므로 초기 운영 복잡도가 높아집니다.

## 결정 시점

첫 공개 릴리스와 외부 기여 수락 전에는 반드시 선택해야 합니다. 여러 기여자의 저작권이 섞인 뒤 라이선스를 변경하려면 모든 권리자의 동의가 필요할 수 있습니다.

현재 저장소에는 라이선스를 넣지 않았으며, 그 상태에서는 일반 대중에게 오픈소스 사용·수정·재배포 권한이 부여되지 않습니다.
